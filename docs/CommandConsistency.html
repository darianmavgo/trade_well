Command consistency

Which pkg/ each cron job uses, and which orchestrator subcommand corresponds to it. trade_orchestrator, 2026-09-24. Read from deploy_gae/cron.yaml, pkg/appserve/cron.go (cronJobs and the handleCron* handlers) and the subcommand dispatch in cmd/orchestrator/main.go; what each entry point calls was traced in the code, not inferred from names. Nothing was run.

Result: 5 of the 6 scheduled jobs reach the same pkg/ function from cron and from the CLI. scan_market does not: the cron route runs scan_market.RunSignalScan, but the CLI subcommand of the same name runs stage_orders.RunScanAndStage, a different function in a different package that also stages orders.

What is inconsistent

  • scan_market. The route, the pkg/ directory and the subcommand share a name, but the subcommand does not run that package's cron function. Running orchestrator scan_market --live stages orders as well; the cron route only writes signals and leaves staging to /cron/stage_orders at 18:15. So a manual scan does not predict what the 18:00 cron does. run-all-jobs inherits the CLI behaviour.
  • Four hyphenated subcommands (health-checks, run-all-jobs, active-trades, staged-orders) still break the snake_case naming rule, with no documented aliases.
  • Email built twice for four of the six jobs (see note under the first table).
